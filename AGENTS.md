# Home Hunter: правила разработки

## Архитектура

- Проект остаётся Django-монолитом с PostgreSQL, server-rendered templates и management-командами.
- Не добавляйте Celery, Redis, REST-фреймворк или отдельный frontend без измеренной проблемы и отдельного архитектурного решения.
- Направление зависимостей: `views/templates -> application services/selectors -> models`; `commands -> services`; `collectors -> normalized DTOs`.
- `collectors` не изменяют ORM и не импортируют `listings.views`.
- Доменные расчёты (scoring, market comparison, location rules) не размещаются во views.
- Review queue и consideration workflow поддерживаются в `listings/views_reviews.py` и `listings/services/reviews.py`; `listings/views.py` содержит только URL-совместимые wrappers.
- Операционные страницы резервного копирования, контроля исчезнувших объявлений,
  недоступных карточек и качества данных размещаются в `listings/views_operations.py`;
  новые эксплуатационные workflow не добавляются в общий `listings/views.py`.
- Справочники локаций, геозоны и карты объявлений размещаются в `listings/views_geo.py`;
  новые географические workflow не добавляются в общий `listings/views.py`.
- Формирование JSON/CSV/XLSX-выгрузок размещается в `listings/views_exports.py`;
  views не должны дублировать сериализацию и формирование файлов.
- Настройки личной оценки размещаются в `listings/views_preferences.py`;
  обработчики scoring не добавляются в общий `listings/views.py`.
- Общие операции detail persistence размещаются в `listings/services/detail_persistence.py`; команды сохраняют только source-specific enrichment.
- Состояние циклов detail-опроса изменяется через `listings/services/detail_progress.py`; команды не дублируют lifecycle прогресса.
- Фильтры, варианты фильтров и похожие объявления обслуживаются `listings/services/listing_queries.py`; views не содержат дублирующую query-логику.
- Доменные группы моделей выносятся в отдельные `listings/models_*.py` без изменения app label, имён таблиц и публичных re-export’ов из `listings.models`.
- Detail/polling-модели относятся к `listings/models_polling.py`; команды и сервисы импортируют их через публичный контракт приложения.

## Изменения данных и side effects

- Ingestion должен быть идемпотентным при повторной обработке одного объявления.
- Границы транзакций должны быть явными; внешние отправки запускаются после commit через `transaction.on_commit`.
- Не удаляйте исторические snapshots, price history, scan records и polling state.
- Миграции должны быть backward-compatible; destructive migration требует отдельного согласования.
- Секреты, cookies, proxy credentials и production dumps не добавляются в git и не пишутся в логи.

## Collectors

- Parser — чистое преобразование HTML/JSON в DTO.
- Collector отвечает за transport, browser/session lifecycle, pagination и block/cooldown policy.
- Общий контракт — `collectors.base.NormalizedListing` и `CollectionResult`.
- Partial/failed scan не должен деактивировать объявления.

## Тестирование

Перед завершением изменения запускайте применимые проверки:

```bash
venv/bin/python manage.py check
venv/bin/python manage.py makemigrations --check --dry-run
venv/bin/pytest
```

Live browser tests запускаются отдельно и не должны быть обязательной частью обычного unit-test прогона.

## Комментарии в коде

- Комментарии и docstring для новых и существенно изменённых функций пишутся на русском языке.
- Комментарий должен кратко объяснять причину, инвариант или важное ограничение; не пересказывайте очевидные строки кода.
- Формулируйте комментарии естественным русским языком: описывайте, что важно для
  пользователя или поддержки проекта, а не переводите дословно англоязычный
  технический термин.
- Если правило можно объяснить обычной фразой («границы меняем местами, чтобы
  диапазон оставался корректным»), используйте её вместо канцелярита и жаргона.
- Предпочитайте один лаконичный комментарий рядом с нетривиальной границей или правилом вместо комментария к каждой строке.
- Если поведение понятно из имени функции и типов, дополнительный комментарий не нужен.
- Англоязычные комментарии в неизменяемом legacy-коде не требуют массовой правки; при изменении участка их следует постепенно заменять на русские.

## Документация сервисов

- Каждый файл в `listings/services/` начинается с русскоязычного module docstring, кратко описывающего назначение сервиса и его границу ответственности.
- Каждый выделенный файл моделей начинается с русскоязычного module docstring и описывает свою доменную группу.
- Публичные функции сервисов имеют короткий русскоязычный docstring, если их назначение или ограничения не очевидны из имени и типов.
- Не смешивайте в одном сервисе HTTP-rendering, сетевой transport и доменные расчёты без явной причины.

## Документация

- Фактическая архитектура описывается в `docs/ARCHITECTURE.md`.
- При изменении границ модулей, фоновых процессов, моделей или внешних интеграций обновляйте архитектурную документацию в том же изменении.
- Каждое заметное изменение фиксируйте в `CHANGELOG.md` в том же коммите, что и код.
- Не описывайте будущую архитектуру как уже существующую.
