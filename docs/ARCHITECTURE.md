# Архитектура Home Hunter

## Фактическая схема

Home Hunter — Django-монолит с PostgreSQL. Web-приложение запускается Gunicorn, фоновые процессы — management-командами из systemd timers/services. Celery, Redis и отдельный REST API в проекте не используются.

```text
SearchQuery
  -> polling profile / route
  -> source collector (Avito, CIAN, DomClick)
  -> NormalizedListing
  -> listings.services.persistence.process_listing()
  -> Listing + ListingSearchQuery + PriceHistory + ListingSnapshot
  -> Django views/templates, XLSX export, Telegram delivery
```

Для Avito `SearchQuery` может содержать обычный HTML URL (`url`) и соответствующий
URL Mobile API (`mobile_api_url`). Транспорт выбирается polling-профилем, поэтому
один запуск использует только одну форму запроса; оба collector'а передают данные
в общий `NormalizedListing` и persistence-контракт.

Для профилей Avito с `cookie_strategy=spfa` cookies и user-agent получает
`collectors.avito.spfa.SpfaClient`: Mobile API использует обязательный
авторизованный proxy, а Chromium получает обычные cookies и добавляет их в новый
контекст. Сохранённые cookies перед следующим запуском ставятся в бесплатную
очередь разблокировки; ответ `202` означает только принятие задания.

## Модули

Назначение и границы сервисных модулей собраны в отдельном фактическом каталоге
[`docs/SERVICES.md`](SERVICES.md). При расхождении каталога с кодом приоритетом
является исправление документации в том же изменении, а не молчаливое расширение
ответственности сервиса.

### Web и frontend

Маршруты находятся в `listings/urls.py`, HTTP-обработчики — в тематических модулях
`listings/views*.py` и `listings/agent_views.py`; `listings/views.py` сохраняет
совместимые публичные импорты и оставшиеся обработчики. Dashboard вынесен в
`listings/views_dashboard.py`, а назначение polling-профилей — в
`listings/views_polling_profiles.py`. UI — Django templates в `listings/templates/listings`
и `templates`; мониторинг запусков находится в `listings/views_scan_statistics.py`.
Пользовательские feed, shortlist и detail-страницы находятся в
`listings/views_listings.py`.
Операционные страницы резервного копирования, контроля исчезнувших объявлений,
недоступных карточек CIAN и качества данных находятся в
`listings/views_operations.py`.
Справочники локаций, пользовательские геозоны и карты находятся в
`listings/views_geo.py`.
Выгрузки пользовательских оценок и рыночного сравнения находятся в
`listings/views_exports.py`.
Настройки личной оценки находятся в `listings/views_preferences.py`.
Расчёт ближайших запусков и ограничения режимов находятся в
`listings/services/polling_schedule.py`.
JavaScript встроен в шаблоны, карта использует Leaflet. Отдельной
frontend-сборки и формального API schema layer нет.

### Collectors

`collectors/avito`, `collectors/cian` и `collectors/domclick` содержат source-specific parsers и Playwright/HTTP collectors. Общий DTO-контракт определён в `collectors/base.py`; выбор реализации выполняет `collectors/registry.py`. Сетевые профили и proxy resolution находятся в `collectors/routing.py`.

### Persistence и scan orchestration

`listings/services/persistence.py` нормализует адрес, рассчитывает цену за м², применяет location rules и сохраняет историю. `listings/services/scans.py` создаёт Scan, обрабатывает `CollectionResult` и выполняет безопасную деактивацию только для завершённых проходов. Detail polling использует общий orchestration-слой и source-specific persistence-сервисы; management-команды оставляют за собой получение данных площадки.

### Модели

`Listing` и инфраструктурные модели пока остаются в `listings/models.py`, а review-домен и detail/polling state вынесены в `listings/models_reviews.py` и `listings/models_polling.py` с re-export из legacy-модуля. `Listing` остаётся центральной моделью.

### Фоновые процессы и эксплуатация

Сканирование, detail polling, геокодирование, Telegram polling/delivery и health checks запускаются через management-команды и `deploy/systemd`. Advisory locks PostgreSQL и filesystem `flock` защищают конкурирующие запуски. Docker разделяет web, collector, Telegram polling и proxy tunnel.

## Границы и ограничения

Review workflow находится в `views_reviews.py` и `services/reviews.py`. Доменное сравнение цен выполняет `services/market.py`, персональную оценку — `services/scoring.py`. Экспорт форматирует эти результаты на границе представления; агрегатные листы имеют отдельную статистическую семантику.

Detail-команды получают данные источника. Сохранение выполняют `cian_detail_persistence.py` и `avito_detail_persistence.py`, общий переход в опубликованное состояние — `mark_detail_published()`. Прогресс циклов обслуживает `detail_progress.py`, выбор кандидатов и общий цикл — `detail_polling.py`.

Telegram-публикации проходят очередь `telegram_delivery.py`. Постоянный `telegram_send` запускается через systemd внутри контейнера web. Перед отправкой проверяются актуальные данные объявления и зоны пользователя; состояния доставки не заменяют географическую классификацию.

Часть географических, рыночных и scoring-расчётов выполняется в Python во время запроса. Внешние Telegram-вызовы распределены по нескольким сервисам. Эти ограничения сами по себе не являются основанием вводить новую очередь или отдельный frontend.

Проверки границ импортов: `listings/tests/test_architecture.py`. Правила дальнейшей разработки: [AGENTS.md](../AGENTS.md).

Безопасность полного цикла CIAN накапливается в checkpoint: небезопасный пакет
запрещает учёт исчезнувших объявлений для всего прохода, даже если последний
пакет завершился без ошибок. Миграция 0066 помечает уже существующие checkpoint
небезопасными, поскольку качество ранее прочитанных пакетов неизвестно.
Новый цикл и смена URL поиска начинают проверку заново.

Просроченные Telegram-захваты `sending` снова выбираются worker после истечения
`locked_until`. Номер попытки защищает результат от записи устаревшим worker;
перед отправкой действующий захват продлевается. Доставка допускает повтор:
если Telegram принял сообщение, но результат не сохранился в БД, восстановление
может создать дубль. Это не гарантия однократной доставки.

При выборе Telegram-публикаций `awaiting_geocode` допускаются в кандидаты
только после появления обеих координат или непустого результата геокодирования.
Проверка остальных условий остаётся в `telegram_listing_eligibility()`. Если
кандидат отфильтрован или снова ожидает координат, worker добирает следующие
записи: лимит пакета ограничивает число захватов для отправки.

`process_listing()` создаёт первичную запись `TelegramListingAlert` в той же
транзакции, что новое объявление, историю и связь с поиском. Фильтры определяют
статус записи (`pending`, `awaiting_geocode`, `skipped`); наличие записи не означает
обязательную отправку. Ошибка создания очереди откатывает сохранение объявления.
Сетевую публикацию выполняет worker после commit. Уведомления об изменении цены
сохраняют отдельный вызов через `on_commit`.

Источник планового расписания — `deploy/systemd/*.timer`. Сервис
`polling_schedule.py` читает OnCalendar и RandomizedDelaySec; независимых
часов запуска в Python нет. Timer-файлы входят в web и collector Docker-образы.
Это календарный план, не состояние systemd сервера: запуск после простоя
(Persistent), фактическую случайную задержку, точность срабатывания и включение
таймера интерфейс не определяет. Разрешения запросов остаются в `polling.py`.

## Ручная проверка Avito

Страница `/avito-checks/` обслуживается `views_operations.py`, операции —
`services/avito_manual_checks.py`. История `AvitoManualCheck` находится в
`models_avito_checks.py` с re-export через `listings.models`; она не заменяет
автоматический detail state. Объявление блокируется на время транзакции,
подписанная версия формы сверяется с `updated_at`. Повтор UUID не создаёт записей.
Положительная проверка обновляет `last_seen_at`, отрицательная сохраняет дату
последнего положительного подтверждения. XLSX-импорт может восстановить доступность.

## Динамика рынка

`views_market.py` обслуживает `/market-trends/`; `services/market_trends.py`
сохраняет ежедневные наблюдения и рассчитывает недельные точки.
`models_market.py` содержит `MarketDailySnapshot` с re-export через `listings.models`.
Срез хранит характеристики объявлений, статус, цену, отпечаток включённых поисков,
версию методики и сводку опросов за 24 часа. Личные скрытия не влияют на выборку.
Источники показаны отдельно; дедупликации квартир между площадками нет.

Команда `capture_market_snapshot` атомарно создаёт срезы текущего дня; повтор
не перезаписывает их. История до первого запуска не реконструируется. Недельные
точки — воскресные срезы и последний срез текущей недели. Сравнение цен тех же
объектов и переходов статуса требует восьми последовательных срезов с неизменным
охватом и методикой и успешными опросами каждого поиска за сутки в каждом срезе.
Даже при этом полнота выдачи не подтверждается: успешный Scan может быть fast
или промежуточным пакетом CIAN. Снятие не трактуется как продажа.

Цена за м² рассчитывается из цены и площади. Доля снижений и медиана изменений
цен используют только объявления, активные на обе даты, с положительными ценами
и неизменными районом, микрорайоном, комнатностью и площадью. Новые — впервые
обнаруженные между датами, снятые — активные на первой и неактивные на второй.
Промежуточные снятия/возвраты в эти показатели не входят. Фильтры применяются
к историческим характеристикам; изменение состава поисков разрывает сравнение.

## Личные просмотры и фотографии

`models_viewings.py` содержит `ViewingApartment`, `ViewingListingLink`,
`ViewingEntry`, `ViewingPhoto`, публично экспортируемые через `listings.models`.
Карточка квартиры принадлежит пользователю, независимо связывает несколько
объявлений и хранит собственные сведения. `viewings.py` обслуживает выборки и
изменения; HTTP находится в `views_viewings.py`, формы — в `forms_viewings.py`.
Существующие reviews и consideration не меняются автоматически.
`ViewingApartment` хранит собственное описание и необязательные внешние ссылки
на три площадки; сохранение ссылок не вызывает сеть или ingestion. Комментарии
и посещения остаются типами `ViewingEntry`, но отображаются отдельными списками.

`viewing_photos.py` проверяет и перекодирует фотографии в JPEG без EXIF. Файлы
и миниатюры хранятся в приватном `MEDIA_ROOT`; Docker web монтирует постоянный
volume `viewing_media`. Выдача файлов проходит owner-check в Django, Caddy
не раздаёт media напрямую. Вложение фото и изменение БД имеют явную транзакцию;
новые файлы удаляются при ошибке, пользовательское удаление — после commit.
Повреждённый запрос не должен оставлять частично сохранённую запись.
Редактирование карточки поддерживает добавление и удаление фото в одной транзакции.
Удаление карточки доступно владельцу через отдельный экран подтверждения и POST
с CSRF/версией; файлы удаляются после commit, исходные объявления сохраняются.

`project_backup.py` создаёт PostgreSQL dump и архив media под эксклюзивным
flock в media volume. Операции изменения фото используют shared flock.
Это файловая синхронизация процессов одного сервера, без фоновой очереди.
Архив содержит manifest с размерами и SHA-256, проверяется и извлекается командой
`verify_project_backup`. Административная выгрузка по умолчанию полная;
вариант только БД остаётся доступным. См. [VIEWINGS.md](VIEWINGS.md).

## Общие исключения рыночной выборки

`models_market_exclusions.py` хранит `MarketExclusion` с re-export из
`listings.models`. Сервис `market_exclusions.py` управляет допуском, причинами
и историей возврата, блокируя `Listing` на время изменения. HTTP управления
находится в `views_operations.py`. Исключения независимы от скрытий и данных
площадок. `market.py`, dashboard, рыночный XLSX, Telegram и исторические графики
используют общий набор исключений. Главная лента и похожие предложения также
исключают эти ID. Очередь Telegram проверяет пометку при захвате и перед отправкой;
уведомления о цене блокируются. Сами дневные срезы и история не меняются.
См. [MARKET_EXCLUSIONS.md](MARKET_EXCLUSIONS.md).


Действующее `MarketExclusion` задаёт единое исключение из рыночной выборки,
пользовательского подбора и рабочих очередей проверки для всех источников.
Общий допуск находится в `services/market_exclusions.py`; фильтры интерфейса,
review queue и detail polling используют его без изменения статуса публикации.
Импорт сохраняет пометку, исторические данные остаются доступны отдельно.
