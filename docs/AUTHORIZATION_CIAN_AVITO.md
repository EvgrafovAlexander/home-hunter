# Авторизация и сетевой доступ CIAN/Avito

Документ описывает текущую реализацию Home Hunter. Здесь слово «авторизация»
включает браузерные cookies и профиль Chromium. Обычная авторизация под
пользовательским аккаунтом CIAN или Avito сейчас не используется.

## Общая схема

Плановый запуск выполняется на сервере через systemd и Docker:

```text
systemd timer
  -> collector container
  -> Playwright/Chromium
  -> SOCKS5 proxy
  -> shared-socks-tunnel (SSH dynamic forwarding)
  -> remote tunnel host
  -> CIAN or Avito
```

`shared-socks-tunnel` — общий SSH/SOCKS-маршрут. Историческое имя
`cian-tunnel` больше не используется как имя Docker-сервиса. На удалённом
сервере может оставаться пользователь SSH с историческим именем, это отдельная
деталь инфраструктуры.

Внутри Docker сеть выглядит так:

```text
shared-socks-tunnel:1080
```

На хосте локальный порт `127.0.0.1:19082` используется для локального агента,
которому нужен тот же маршрут.

## Сетевой маршрут

Контейнер запускает OpenSSH с dynamic forwarding:

```text
ssh -NT -D 0.0.0.0:1080 ... user@remote-host
```

Проверяются:

- `BatchMode=yes`;
- строгая проверка `known_hosts`;
- отдельный SSH-ключ из каталога, смонтированного read-only;
- `ServerAliveInterval` и `ServerAliveCountMax`;
- `ExitOnForwardFailure=yes`;
- healthcheck локального SOCKS5 handshake.

Healthcheck подтверждает наличие локального SOCKS-листенера. Он не подтверждает,
что конкретная площадка пропускает запросы. Доступ к площадке проверяется только
реальным запросом коллектора.

Основные параметры:

| Параметр | Назначение |
|---|---|
| `SHARED_SSH_DESTINATION` | SSH-пользователь и удалённый адрес |
| `SHARED_SSH_DIR` | каталог ключа и `known_hosts` |
| `SHARED_PROXY_URL` | адрес маршрута для профилей по умолчанию |
| `shared-socks-tunnel:1080` | SOCKS5-адрес внутри Docker |

Пароли, приватные ключи и токены провайдеров не хранятся в базе данных.
Профили содержат только ссылку на секрет (`secret_ref`).

Для HTTP/SOCKS-прокси с авторизацией `secret_ref` может быть префиксом группы
переменных окружения. Например, маршрут с `secret_ref=SERVER_PROXY` читает:

```dotenv
SERVER_PROXY_URL=http://proxy.example:8080
SERVER_PROXY_USERNAME=proxy_user
SERVER_PROXY_PASSWORD=proxy_password
SERVER_PROXY_HEALTHCHECK_URL=https://api.ipify.org
```

В базу при этом попадает только имя группы. В Playwright credentials передаются
отдельными полями, а не частью URL. Старый вариант с переменной, имя которой
совпадает с `secret_ref` и содержит полный URL, сохраняется для совместимости.

## Профили запуска

Профиль назначается на площадку и используется всеми её режимами. Поле режима
у профиля со значением `all` означает такой общий профиль. Точечные профили для
`fast`, `full` или `detail` остаются доступными как расширенный override.
Миграция создаёт следующие профили по умолчанию:

| Профиль | Площадка | Сессия | Маршрут |
|---|---|---|---|
| `avito_default` | Avito, все режимы | постоянный Chromium-профиль | общий SSH/SOCKS |
| `cian_default` | CIAN, все режимы | постоянный Chromium-профиль | общий SSH/SOCKS |
| `cian_detail_default` | CIAN detail, расширенный override | постоянный Chromium-профиль | общий SSH/SOCKS |
| `domclick_default` | Домклик, все режимы | настройки площадки | общий SSH/SOCKS |

Профиль можно выбрать:

- в админке Django;
- на странице **Профили опросов** для staff-пользователя, одной карточкой на площадку;
- вручную при запуске командой `--profile PROFILE_CODE`.

Если профиль не найден, сборщик временно использует совместимую конфигурацию из
старых переменных `AVITO_PROXY_URL`, `CIAN_PROXY_URL` или
`DOMCLICK_PROXY_URL`. Это позволяет откатить базу профилей без потери маршрута.

Если заданы `MOBILE_PROXY_URL`, `MOBILE_PROXY_USERNAME` и
`MOBILE_PROXY_PASSWORD`, для Avito они имеют приоритет над историческим
маршрутом `avito_default`. Учетные данные остаются в окружении, а выбранный
маршрут получает тип `mobile_proxy`. Для профиля Avito со стратегией `SPFA`
запрос выдачи cookies и последующий `unblock` передают тот же авторизованный
мобильный маршрут в SPFA, чтобы cookies соответствовали выходному IP Avito.

## Avito

### Запуск браузера

Avito использует Playwright и Chromium. Состояние теперь привязано к коду
выбранного `PollingProfile`: для production-профиля оно хранится в
`AVITO_STATE_DIR/profiles/<profile-code>/` (`/app/.avito-state` в контейнере).
Это изолирует cookies и cooldown при переключении между разными маршрутами.

При прямом создании `AvitoCollector` без кода профиля сохраняется старый путь
`AVITO_STATE_DIR` для совместимости с ручными запусками и тестами.

В состоянии хранятся:

- `next_request_at` — минимальное время следующего запроса;
- `blocked_until` — общий cooldown после блокировки;
- `last-response.json` — диагностические данные последнего ответа.

Основной production-профиль `avito_default` постоянный: после валидной страницы
Chromium сохраняет cookies, local storage и остальные данные сессии в volume.
Профиль изолирован кодом polling-профиля, поэтому его нельзя случайно смешать
с другим маршрутом. Если Avito возвращает WAF, captcha или невалидную выдачу,
профиль помечается на ротацию: следующий запуск архивирует его в
`profiles/<profile-code>/archive/` и начинает новую сессию. Старый профиль не
удаляется. Временный режим остаётся доступным для диагностических и
восстановительных профилей.
Постоянный профиль сохраняется только внутри каталога назначенного polling
профиля; один и тот же Chromium-профиль не должен использоваться с разными
выходными IP.

### Cookies и аккаунт

Avito не получает логин, пароль или API-токен. Cookies создаются внутри
браузерного профиля самим сайтом. Профиль по умолчанию не является постоянным,
поэтому cookies не считаются долговременной авторизацией.

Для экспериментального Avito Mobile API в профиле можно выбрать отдельный
транспорт и стратегию cookies. По умолчанию остаются `Chromium / HTML` и
`Профиль Chromium`; CIAN и Домклик эти настройки не используют. Для стратегии
`Собственные cookies` API collector читает файл
`AVITO_STATE_DIR/profiles/<profile-code>/cookies.json`. Для `SPFA` требуется
секрет `AVITO_SPFA_API_KEY` и настроенный endpoint конвертации URL поиска.

Для ручной диагностики можно использовать headed-запуск и ожидание captcha.
После истечения таймера автоматический обход блокировки не выполняется.

### Обработка блокировок

Состояние страницы классифицируется по HTTP-кодам `403`, `429`, `439` и по
текстам проверки безопасности. При блокировке:

1. запуск помечается остановленным;
2. в `request-state.json` записывается cooldown;
3. следующие запросы не отправляются до его окончания;
4. прямой fallback не выполняется;
5. оставшиеся поиски в том же запуске не обрабатываются.

Текущая наблюдаемая проблема Avito — ответ `439` от WAF через внешний IP
общего маршрута. Это означает, что Chromium и SOCKS-маршрут запускаются, но
выходной IP или сессия не принимаются Avito.

## CIAN

### Запуск браузера

CIAN использует Playwright и Chromium с постоянным профилем:

```text
CIAN_STATE_DIR/chromium
```

Это позволяет сохранять cookies, local storage и принятые браузером проверки
между запусками. Профиль одновременно используется последовательными задачами,
поэтому systemd и общий `flock` не допускают параллельные сборщики.

CIAN fast и CIAN detail используют назначенный профилю площадки маршрут и одну
модель постоянной сессии. При необходимости detail можно перевести на отдельный
профиль `cian_detail_default` как расширенный override.

### Cookies и проверка

Автоматической авторизации в аккаунте CIAN нет. Сайт сам выдаёт cookies и
состояние проверки в Chromium-профиль. При подозрительном трафике сборщик
сохраняет cooldown и немедленно останавливает batch.

Валидация ответа проверяет:

- HTTP-коды блокировки;
- страницу captcha и тексты проверки робота;
- ожидаемый host и path;
- совпадение query-параметров и номера страницы;
- наличие корректных карточек и embedded JSON CIAN.

Отсутствие объявления с HTTP 404 на detail-странице считается штатным снятием
объявления и не является сетевой блокировкой.

## Выбор профиля во время запуска

Команда поиска:

```text
python manage.py collect_listings \
  --source avito --mode fast --profile avito_default
```

Детальный опрос CIAN:

```text
python manage.py poll_cian_details --profile cian_detail_default
```

Для Avito detail используется отдельный второй этап и профиль с `mode=detail`,
`transport=mobile_api` и `cookie_strategy=own_cookies` или `spfa`:

```bash
python manage.py poll_avito_details --profile avito_mobile_detail
```

Он сохраняет состояние доступности и полный последний JSON так же, как CIAN,
а затем дополняет карточку координатами и полной галереей. Основной Avito
polling при этом не переключается на detail автоматически.

Без `--profile` используется профиль, назначенный площадке. Если назначения нет,
система проверяет старое назначение source/mode, затем профиль по умолчанию и
только после этого применяет совместимый env-based fallback.

## Публичный пул прокси

Для экспериментальной диагностики добавлен общий маршрут `public_proxy_pool`.
Он может быть назначен профилю любой площадки. На странице **Профили опросов**
созданы варианты для АВИТО, ЦИАН и Домклика; ни один из них не назначается по
умолчанию.

Маршрут получает список адресов из API Geonix для России
(`https://free.geonix.com/api/front/main/proxy/list`), отбирает
небольшое число высокоанонимных кандидатов, проверяет их через нейтральный
HTTPS-адрес и выбирает один прокси на весь запуск. При сетевой ошибке допускается
ограниченное число следующих кандидатов. Ответы `403`, `429` и `439` не запускают
массовый перебор: сохраняется обычный cooldown АВИТО.

Пул предназначен для ручных диагностических прогонов и не заменяет стабильный
серверный или мобильный прокси.

## Что пока не делает система

- не выполняет автоматическую авторизацию в аккаунтах CIAN или Avito;
- не меняет внешний IP общего SSH-маршрута;
- не переключается молча на прямое подключение;
- не считает healthcheck SOCKS доказательством доступности Avito или CIAN;
- не загружает приватные ключи через веб-интерфейс.

Серверный proxy route уже может быть подготовлен через группу `SERVER_PROXY_*`,
но пока не назначен профилям по умолчанию. Для мобильного прокси следующая
реализация должна добавить отдельный route adapter с URL смены IP и отдельной
политикой повторов. Это не должно менять поведение профилей `cian_default` и
`avito_default`.
