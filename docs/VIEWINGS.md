# Мои просмотры и перенос на ноутбук

## Личная карточка квартиры

Раздел `/viewings/` доступен в основной навигации. «Лучшие варианты» перенесён
в «Ещё» и остаётся доступным сотрудникам. Карточки, записи и фотографии
принадлежат создавшему их пользователю. Даже другой staff-пользователь не может
открыть личную карточку или фото через их URL. Полный административный backup
содержит данные всех пользователей.

Для создания достаточно названия. Адрес, район, комнаты, площадь, этажность,
цены и контакт можно заполнить позже. Решения: «Думаю», «Подходит», «Отказ»,
«Архив». Архив скрыт из списка по умолчанию, но доступен через фильтр.

При создании можно подставить данные по внутреннему ID HomeHunter или ссылке
`/listings/123/`. В карточке можно связать до 20 объявлений; поиск показывает
предпросмотр и предупреждение о других личных карточках с той же привязкой.
Обновления источника не меняют сведения, введённые пользователем. Связи можно
убрать, сохранив личную карточку. Из объявления доступна кнопка добавления
в просмотры. Данные существующих оценок и consideration автоматически не меняются.

Лента содержит комментарии и просмотры с датой, временем по Екатеринбургу
и статусом «Запланирован», «Состоялся», «Отменён». Повторные посещения — отдельные
записи. Формы редактирования проверяют версию, чтобы старая вкладка не затёрла
последние изменения. Карточки архивируются через поле «Решение».

## Фотографии

Поддерживаются JPEG, PNG и WebP: до 12 файлов за один запрос, до 10 МБ и
32 мегапикселей на исходный файл, до 100 фотографий на квартиру.
HEIC нужно предварительно преобразовать в поддерживаемый формат.

Изображения поворачиваются с учётом EXIF и преобразуются в JPEG до 1920 px
по длинной стороне. Миниатюры — до 480 px. EXIF и исходные файлы не сохраняются.
Прозрачность заменяется белым фоном. У фото есть подпись; любое фото можно
сделать обложкой или удалить. Галерея поддерживает увеличение и переключение.

В Docker фотографии находятся в volume `viewing_media`, смонтированном
в `/app/media` контейнера web. Каталог принадлежит UID 10001. Volume переживает
пересоздание контейнера и не входит в image. Локально используется `media/`
в корне проекта; другой каталог задаётся `MEDIA_ROOT`. Он исключён из Git.
Compose принудительно задаёт `MEDIA_ROOT=/app/media` для web: данные остаются
в постоянном volume независимо от локальной настройки в `.env`.

Публичной раздачи `/media/` нет. Файлы выдаются через Django после проверки
владельца, с `Cache-Control: private, no-store`. Сетевых запросов к площадкам
при загрузке пользовательских фото нет.

## Один полный backup

Откройте «Ещё → Резервная копия БД» под staff-пользователем и нажмите
«Скачать полный backup — БД и фотографии». При публичном HTTP используйте
SSH-туннель, описанный в [OPERATIONS.md](OPERATIONS.md).

Скачивается один `home_hunter_full_…tar.gz`:

- `database.dump` — PostgreSQL custom dump всей БД;
- `media/` — все сохранённые фотографии и миниатюры;
- `manifest.json` — версия формата, время создания, размеры и SHA-256 файлов.

На время создания архива берётся эксклюзивный lock в media volume: добавление
и удаление фото временно возвращает сообщение о занятости. Обычное чтение
карточек доступно. Это обеспечивает согласованность дампа и файлов при работе
через приложение. Прямые изменения файлов/БД извне этот lock не соблюдают.
Если отсутствует файл фотографии или найдена символьная ссылка, создание
полного backup завершается ошибкой вместо выдачи неполного архива.

Архив временно создаётся на сервере и удаляется после завершения HTTP-ответа.
Для его создания требуется свободное место примерно под архив и отдельный
дамп БД. При аварийном завершении процесса временные файлы могут остаться
в `/tmp/home_hunter_full_*` и `/tmp/home_hunter_backup_*`; не удаляйте их во время
активной выгрузки. Отдельная кнопка «Скачать только БД» сохраняет прежний формат
дампа, но не подходит для переноса фотографий.

## Проверить и распаковать на ноутбуке

Используйте текущую версию проекта и подготовленное локальное окружение
из [DEVELOPMENT.md](DEVELOPMENT.md):

```bash
venv/bin/python manage.py verify_project_backup ~/Downloads/home_hunter_full_YYYY-MM-DD_HH-MM-SS.tar.gz --extract-to ./recovered
```

Команда проверяет состав и SHA-256 **до извлечения**, не подключается к БД
и не восстанавливает её. Каталог `recovered` должен быть новым или пустым.
Отсутствие `--extract-to` выполняет только проверку.

Для восстановления в **новую локальную** PostgreSQL БД (локальный Compose
должен быть настроен и запущен, без production-подключений):

```bash
docker compose exec -T db sh -c 'createdb -U "$POSTGRES_USER" home_hunter_restore'
docker compose exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" --no-owner --no-privileges --exit-on-error -d home_hunter_restore' < recovered/database.dump
POSTGRES_DB=home_hunter_restore MEDIA_ROOT="$PWD/recovered/media" venv/bin/python manage.py migrate
POSTGRES_DB=home_hunter_restore MEDIA_ROOT="$PWD/recovered/media" venv/bin/python manage.py runserver
```

В `.env` должны быть локальные HOST/PORT/USER/PASSWORD. Восстановленная БД
содержит прежних пользователей и их пароли; вход выполняется ими.
Конфигурация `.env`, cookies файловых профилей браузера и SSH-ключи в этот
архив не включаются. Для локального просмотра карточек они не нужны.
Не запускайте из восстановленной копии фоновые опросы и отправки Telegram
без отдельной настройки локального окружения.

При восстановлении на другом сервере файлы из `recovered/media/` необходимо
поместить в его `viewing_media` volume с правами UID 10001, а БД восстановить
в согласованное состояние из того же архива.
